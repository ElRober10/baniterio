# Inventario de la fiesta — Diseño

**Fecha:** 2026-09-09
**Rama:** `feature/inventario` (continúa el trabajo de la sección Inventario)
**Contexto:** amplía la sección Inventario ya implementada (ver
`2026-09-09-inventario-design.md`) para poder mover stock del inventario
general de la peña al inventario de un evento concreto, y devolverlo.

## Objetivo

Desde el listado de una categoría del inventario general, "Enviar a evento"
un artículo (o todos los de la categoría) mueve su cantidad al inventario de
un evento elegido en un modal. Cada evento tiene una pantalla "Inventario de
la fiesta" con lo que se le ha enviado, y cada línea tiene "Devolver a
inventario" para deshacer el movimiento.

## Decisiones tomadas (brainstorming 2026-09-09)

- **Enviar = mover.** Al enviar se resta *toda* la cantidad de la fila del
  inventario general y se suma en el del evento. Devolver hace lo inverso.
- **Se envía toda la cantidad de la fila.** No se pregunta cuánto. "Enviar
  todo a evento" recorre todas las filas de la categoría con cantidad > 0.
- **Eventos elegibles:** los "abiertos" = no pasados y no ocultos.
- **Devolver = línea entera.** No hay devolución parcial en v1.
- **Permiso:** enviar y devolver exigen el área `INVENTARIO` (admin
  implícito). Ver el inventario de la fiesta lo puede cualquier usuario
  logueado (el botón que lleva a esa pantalla ya sale para todos los
  apuntados).
- **Filas a 0 en el general:** no se listan (ni al ver ni al editar). Al
  devolver, la fila de origen recupera cantidad y vuelve a aparecer.
- **Sin editar cantidades** dentro del inventario de la fiesta (las mermas
  se corrigen devolviendo y reenviando). Sin devoluciones parciales. Sin
  histórico de movimientos.

## Modelo de datos

### Tabla `articulo_evento` (migración `V37__inventario_evento.sql`)

```sql
CREATE TABLE articulo_evento (
    id                     BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    evento_id              BIGINT        NOT NULL REFERENCES evento (id) ON DELETE CASCADE,
    articulo_inventario_id BIGINT        NOT NULL REFERENCES articulo_inventario (id),
    categoria              VARCHAR(20)   NOT NULL,
    nombre                 VARCHAR(120)  NOT NULL,
    tamano                 VARCHAR(20)   NOT NULL,
    cantidad               NUMERIC(8, 2) NOT NULL DEFAULT 0,
    orden                  INT           NOT NULL DEFAULT 0,
    CONSTRAINT ck_articulo_evento_categoria
        CHECK (categoria IN ('ALCOHOL', 'CERVEZA', 'REFRESCOS', 'LIMPIEZA', 'COMIDA')),
    CONSTRAINT ck_articulo_evento_cantidad CHECK (cantidad >= 0),
    CONSTRAINT uq_articulo_evento UNIQUE (evento_id, articulo_inventario_id)
);
CREATE INDEX ix_articulo_evento_evento ON articulo_evento (evento_id);
```

Sin siembra.

- `articulo_inventario_id`: la fila del general de la que salió. Es la que
  recibe la cantidad de vuelta al devolver. `UNIQUE (evento_id,
  articulo_inventario_id)` garantiza una sola línea por artículo y evento:
  reenviar suma.
- `categoria` / `nombre` / `tamano`: copia en el momento del envío, para que
  el listado de la fiesta no dependa de que la fila de origen siga igual.
- `ON DELETE CASCADE` en `evento_id`: si se borra de verdad un evento, su
  inventario se va con él. (Nota: "borrar" un evento en la app sólo lo
  oculta; el cascade es defensivo.)

## API

Todo en el módulo `com.baniterio.api.inventario` salvo el endpoint de eventos
abiertos, que vive en el módulo `evento`.

### `GET /api/v1/eventos/abiertos`

Cualquier usuario logueado. Devuelve los eventos elegibles para el modal.

```json
[{ "id": 3, "nombre": "San Miguel", "fecha": "2026-09-25" }]
```

- "Abierto" = no `pasado` y no `oculto`. `pasado` se calcula igual que en el
  listado de eventos (fecha fin, o fecha + 3 días, ya superada).
- Orden: por fecha ascendente.
- Se añade `EventoService.abiertos(Long usuarioId): List<EventoAbiertoDto>`
  reutilizando la lógica de "pasado"/"oculto" que ya tiene el servicio.
- DTO: `record EventoAbiertoDto(Long id, String nombre, LocalDate fecha)`.

### `POST /api/v1/inventario/{articuloId}/enviar`

Área `INVENTARIO`. Body: `record EnviarAEventoRequest(@NotNull Long eventoId)`.

Mueve toda la cantidad de la fila `articuloId` del inventario general al
evento:

1. 403 `SIN_PERMISO_INVENTARIO` si no tiene el área.
2. 404 `ARTICULO_INVENTARIO_NO_ENCONTRADO` si la fila no existe o no es de la peña.
3. 404 `EVENTO_NO_ENCONTRADO` si el evento no existe / está oculto / es de otra peña.
4. 400 `NADA_QUE_ENVIAR` si `cantidad == 0`.
5. Busca `articulo_evento` por `(eventoId, articuloId)`:
   - existe → `cantidad += art.cantidad`
   - no existe → crea la fila, copiando categoría/nombre/tamaño,
     `orden = max(orden de ese evento y categoría) + 1`
6. Pone `art.cantidad = 0` en el general.
7. Responde `204 No Content`.

### `POST /api/v1/inventario/enviar-categoria`

Área `INVENTARIO`. Body:
`record EnviarCategoriaRequest(@NotNull CategoriaInventario categoria, @NotNull Long eventoId)`.

- 403 / 404 evento como arriba.
- Recorre todas las filas de esa categoría de la peña con `cantidad > 0` y
  aplica el mismo movimiento que `enviar` a cada una.
- Si no hay ninguna con cantidad > 0: **no es error**, responde `204` sin
  hacer nada (la UI ya no muestra el botón si la lista está vacía, pero el
  endpoint es tolerante).
- Responde `204 No Content`.

### `GET /api/v1/inventario/evento/{eventoId}`

Cualquier usuario logueado.

```json
{
  "puedoEditar": true,
  "categorias": [
    { "categoria": "ALCOHOL", "etiqueta": "Alcohol",
      "articulos": [ { "id": 12, "nombre": "Tanqueray", "tamano": "70 cl", "cantidad": 1.5 } ] }
  ]
}
```

- 404 `EVENTO_NO_ENCONTRADO` si el evento no existe / oculto / de otra peña.
- `puedoEditar` = tiene área `INVENTARIO` (controla los botones "Devolver").
- Se devuelven **sólo las categorías que tienen algún artículo** (a
  diferencia del general, que siempre devuelve las 5). Si el evento no tiene
  nada, `categorias` es `[]`.
- `id` en cada artículo es el `articulo_evento.id` (lo que consume "devolver").
- Reutiliza `ArticuloDto` (id, nombre, tamano, cantidad) y una variante de
  `CategoriaInventarioDto` **sin** `tamanos` (aquí no se edita):
  `record CategoriaEventoDto(String categoria, String etiqueta, List<ArticuloDto> articulos)`.
  Respuesta: `record InventarioEventoResponse(boolean puedoEditar, List<CategoriaEventoDto> categorias)`.

### `POST /api/v1/inventario/evento/{eventoId}/{articuloEventoId}/devolver`

Área `INVENTARIO`.

1. 403 `SIN_PERMISO_INVENTARIO`.
2. 404 `ARTICULO_EVENTO_NO_ENCONTRADO` si la fila no existe o no es de ese evento.
3. `art.articuloInventario.cantidad += art.cantidad` (la fila de origen del
   general recupera la cantidad; si estaba a 0 vuelve a listarse).
4. Borra la fila de `articulo_evento`.
5. Responde `204 No Content`.

### Cambios en endpoints existentes del inventario general

- `GET /api/v1/inventario`: al construir cada `CategoriaInventarioDto`,
  filtrar los artículos con `cantidad == 0` (BigDecimal `compareTo`). Las
  categorías se siguen devolviendo siempre las 5.
- `POST /api/v1/inventario` (crear): antes de crear, buscar una fila con
  `(pena, categoria, nombre, tamano)` iguales (`nombre` tras `trim()`). Si
  existe, **actualizar su cantidad** (`= req.cantidad()`) y devolverla, en
  vez de crear una fila nueva. Nuevo método de repositorio:
  `Optional<ArticuloInventario> findByPenaIdAndCategoriaAndNombreIgnoreCaseAndTamano(Long penaId, CategoriaInventario categoria, String nombre, String tamano)`.

### Excepciones nuevas

| Excepción | HTTP | codigo |
|---|---|---|
| `NadaQueEnviarException` | 400 | `NADA_QUE_ENVIAR` |
| `ArticuloEventoNoEncontradoException` | 404 | `ARTICULO_EVENTO_NO_ENCONTRADO` |

`EVENTO_NO_ENCONTRADO` ya existe en el módulo evento
(`EventoNoEncontradoException`); reutilizar. Si su handler no está en
`ApiExceptionHandler`, añadirlo.
