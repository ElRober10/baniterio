# Lista de la compra: "Comprado", devolución y bloqueo — Diseño

**Fecha:** 2026-09-10
**Rama:** `feature/lista-compra` (continúa sobre el bloque 1, todavía sin mergear)
**Depende de:** `docs/superpowers/specs/2026-09-09-lista-compra-design.md` (bloque 1)

## Objetivo

Añadir a la lista de la compra por evento tres capacidades que el bloque 1 no cubre:

1. **Marcar una línea como "Comprada"**: envía su cantidad al inventario de la fiesta
   (`articulo_evento`).
2. **Devolver a la lista** desde el inventario de la fiesta: revierte solo la parte que
   se compró desde la lista; las sobras de otros años (lo que llegó del stock general) no
   se tocan.
3. **Bloquear la lista de la compra** (solo administradores del área `INVENTARIO`): aunque
   se apunte más gente, la lista deja de recalcularse. El administrador puede seguir
   ajustando reglas, añadiendo y quitando artículos a mano (las "excepciones"); lo único
   que se congela es el recálculo automático a partir de los apuntados.

## Contexto

Hoy `ListaCompraService.verLista` calcula la lista **entera al vuelo** en cada lectura a
partir de las reglas activas (`regla_compra_evento`) y los apuntados; no hay ninguna
persistencia por línea. El inventario de la fiesta (`articulo_evento`, V37) guarda una fila
por `(evento, articulo_inventario_id)` con la cantidad movida desde el stock general;
"devolver" suma toda la cantidad al artículo de origen y borra la fila.

Un estado por línea (comprada / no comprada) y un bloqueo que congele el cálculo no encajan
en ese modelo sin persistir las líneas mostradas. La lista comprada tampoco tiene artículo
de origen en el inventario general.

## Decisiones tomadas

- **"Comprado" es un toggle**: envía exactamente la cantidad calculada que muestra la línea.
  No se teclea una cantidad distinta.
- **Devolver** solo revierte lo comprado desde la lista. Si la fila del inventario de la
  fiesta también tiene parte de stock, esa parte no se toca.
- **Bloqueo**: congela únicamente el auto-cálculo. El administrador sigue pudiendo ajustar
  cantidades de reglas, añadir y quitar líneas.
- **Fusión en el inventario de la fiesta**: si ya hay "Cerveza / lata" venida del stock y se
  compra "Cerveza / lata" de la lista, se ve **una sola fila** con la cantidad sumada. Por
  dentro se distingue cuánto es stock (vuelve al inventario general) y cuánto es comprado
  (vuelve a la lista).
- **Identidad de línea**: clave `(categoria, nombre, tamano)` de la línea visible. Funciona
  igual para reglas normales y para las marcas del alcohol dinámico. Si cambian los
  apuntados y una línea cambia de tamaño (p. ej. alcohol 70 cl ↔ 1 L), se trata como una
  línea distinta.

## Arquitectura: enfoque A — tabla de líneas materializadas

`linea_compra_evento` pasa a ser la **fuente única** de la lista mostrada. Mientras la lista
no está bloqueada, cada lectura *sincroniza* esa tabla con el resultado del cálculo. Al
bloquear, la sincronización se detiene y las filas se sirven tal cual. Las líneas compradas
quedan congeladas en cualquier caso.

Un solo mecanismo cubre: identidad estable de línea, estado "comprada", bloqueo y el hueco
donde vivirán las futuras "excepciones" (edición admin de líneas concretas con la lista
bloqueada).

## Modelo de datos (migración V39)

### `evento`

```sql
ALTER TABLE evento ADD COLUMN lista_compra_bloqueada BOOLEAN NOT NULL DEFAULT FALSE;
```

### `articulo_evento`

```sql
ALTER TABLE articulo_evento ALTER COLUMN articulo_inventario_id DROP NOT NULL;
ALTER TABLE articulo_evento ADD COLUMN cantidad_comprada NUMERIC(8, 2) NOT NULL DEFAULT 0;
ALTER TABLE articulo_evento ADD CONSTRAINT ck_articulo_evento_comprada CHECK (cantidad_comprada >= 0);
ALTER TABLE articulo_evento DROP CONSTRAINT uq_articulo_evento;
ALTER TABLE articulo_evento ADD CONSTRAINT uq_articulo_evento_producto
    UNIQUE (evento_id, categoria, nombre, tamano);
```

- `cantidad` sigue siendo la parte venida del stock general.
- `cantidad_comprada` es la parte comprada desde la lista (sin artículo de origen).
- Total mostrado en la pantalla = `cantidad + cantidad_comprada`.
- La clave de fusión pasa a ser `(evento_id, categoria, nombre, tamano)`: tanto
  `moverAlEvento` (stock) como "comprado" caen en la misma fila.

### `linea_compra_evento` (nueva)

```sql
CREATE TABLE linea_compra_evento (
    id                 BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    evento_id          BIGINT        NOT NULL REFERENCES evento (id) ON DELETE CASCADE,
    categoria          VARCHAR(20)   NOT NULL,
    nombre             VARCHAR(120)  NOT NULL,
    tamano             VARCHAR(20)   NOT NULL,
    cantidad           NUMERIC(8, 2) NOT NULL,
    orden              INT           NOT NULL DEFAULT 0,
    dinamica           BOOLEAN       NOT NULL DEFAULT FALSE,
    necesita_ficha     BOOLEAN       NOT NULL DEFAULT FALSE,
    ajustada           BOOLEAN       NOT NULL DEFAULT FALSE,
    comprada           BOOLEAN       NOT NULL DEFAULT FALSE,
    articulo_evento_id BIGINT        REFERENCES articulo_evento (id) ON DELETE SET NULL,
    CONSTRAINT ck_lce_categoria
        CHECK (categoria IN ('ALCOHOL', 'CERVEZA', 'REFRESCOS', 'LIMPIEZA', 'COMIDA')),
    CONSTRAINT ck_lce_cantidad CHECK (cantidad >= 0),
    CONSTRAINT uq_lce UNIQUE (evento_id, categoria, nombre, tamano)
);
CREATE INDEX ix_lce_evento ON linea_compra_evento (evento_id);
```

Sin siembra: las filas nacen de la primera sincronización.

### `ListaCompraService`

Nueva dependencia: `LineaCompraEventoRepository lineas`.

**`sincronizar(Evento e, DatosEvento datos)`** (privado, `@Transactional`):

1. Calcular las líneas como hoy: por cada regla activa,
   `CalculadoraListaCompra.lineasDe(r, datos)`, luego `ceil(bruto)` y, si la regla no es
   dinámica y tiene `cantidadAjustada`, esa cantidad. Resultado: lista de tuplas
   `(categoria, nombre, tamano, cantidad, orden, dinamica, necesitaFicha, ajustada)`.
2. Cargar las `linea_compra_evento` del evento a un `Map` por clave `(categoria, nombre, tamano)`.
3. Por cada línea calculada:
   - fila existe y `!comprada` → actualizar `cantidad`, `orden`, `dinamica`,
     `necesitaFicha`, `ajustada`.
   - fila existe y `comprada` → no tocar.
   - no existe → insertar con `comprada = false`, `articuloEventoId = null`.
4. Filas existentes cuya clave no está en el cálculo:
   - `!comprada` → borrar.
   - `comprada` → conservar (la compra se mantiene aunque la lista cambie).

**`verLista(Long usuarioId, Long eventoId)`** (`@Transactional`, cualquier peñista):

1. `eventoAbierto` + `materializar` (reglas, sin cambios).
2. Si `!e.isListaCompraBloqueada()` → `sincronizar(e, datosDe(e))`.
3. Construir la respuesta desde **todas** las `linea_compra_evento` del evento
   (`findByEventoIdOrderBy...`), agrupadas por `CategoriaInventario`, saltando categorías
   sin líneas.
4. `puedoEditar = permisos.puede(usuarioId, INVENTARIO)`.

**`marcarComprada(Long usuarioId, Long eventoId, Long lineaId)`** (`@Transactional`, área INVENTARIO):

1. `exigirArea`; `eventoAbierto`.
2. `linea = lineas.findByIdAndEventoId(lineaId, eventoId)` o `LineaCompraNoEncontradaException`.
3. Si `linea.isComprada()` → no-op (idempotente).
4. Upsert en `articulo_evento` por `(evento, categoria, nombre, tamano)`:
   - existe → `fila.cantidadComprada += linea.cantidad`.
   - no existe → fila nueva: `articuloInventario = null`, `categoria/nombre/tamano` de la
     línea, `cantidad = 0`, `cantidadComprada = linea.cantidad`, `orden` = siguiente de la
     categoría en ese evento.
5. `linea.comprada = true`; `linea.articuloEventoId = fila.getId()`.

La API no ofrece "desmarcar comprada" desde la lista; la reversión se hace desde el
inventario de la fiesta ("Devolver a la lista"), que es donde el usuario ve lo que ha
comprado.

**`cambiarBloqueo(Long usuarioId, Long eventoId, boolean bloqueada)`** (`@Transactional`, área INVENTARIO):

1. `exigirArea`; `Evento e = eventoAbierto`.
2. Si `bloqueada` y `!e.isListaCompraBloqueada()` → `sincronizar(e, datosDe(e))` una última
   vez para congelar el estado actual.
3. `e.setListaCompraBloqueada(bloqueada)`.

**`verAdmin`**: sin cambios de lógica; su respuesta añade `boolean bloqueada`.

### `InventarioService`

Nueva dependencia: `LineaCompraEventoRepository lineas`.

**`devolverALista(Long usuarioId, Long eventoId, Long articuloEventoId)`** (`@Transactional`, área INVENTARIO):

1. `exigirArea` (permiso `INVENTARIO`, como el resto).
2. `fila = articulosEvento.findById(articuloEventoId)` filtrada por `evento.id == eventoId`,
   o `ArticuloEventoNoEncontradoException`.
3. Si `fila.getCantidadComprada().signum() == 0` → `NadaQueDevolverException` (400).
4. `lineas.findByEventoIdAndArticuloEventoId(eventoId, fila.getId())` → si está:
   `linea.comprada = false`, `linea.articuloEventoId = null` (la próxima lectura la
   resincroniza y vuelve a mostrar "Comprado").
5. `fila.setCantidadComprada(BigDecimal.ZERO)`. Si `fila.getCantidad().signum() == 0`
   (no había stock) → borrar la fila; si no, dejarla con solo la parte de stock.

**`devolver` (stock, existente)**: ahora resta solo `fila.getCantidad()` al artículo de
origen. La fila se borra únicamente si `fila.getCantidadComprada().signum() == 0`; si tiene
parte comprada, se deja con `cantidad = 0`.

**`moverAlEvento` (existente)**: la búsqueda de fila pasa a ser por
`(evento, categoria, nombre, tamano)` en lugar de por `articulo_inventario_id`. Si la fila
existente no tenía `articuloInventario` (nació de una compra), se le asigna ahora. Suma en
`fila.cantidad` (parte de stock), no en `cantidadComprada`.

**`verEvento`**: el `ArticuloDto` de cada fila incluye `cantidadComprada`; `cantidad` sigue
siendo el total mostrado (`cantidad + cantidad_comprada`).

## API

| Método | Ruta | Permiso | Respuesta |
|---|---|---|---|
| GET | `/api/v1/eventos/{eventoId}/lista-compra` | peñista | `ListaCompraResponse` (con `bloqueada`, líneas con `id` y `comprada`) |
| POST | `/api/v1/eventos/{eventoId}/lista-compra/lineas/{lineaId}/comprado` | área INVENTARIO | 204 |
| PUT | `/api/v1/eventos/{eventoId}/lista-compra/bloqueo` | área INVENTARIO | 204; body `{ "bloqueada": true }` |
| POST | `/api/v1/eventos/{eventoId}/inventario/{articuloEventoId}/devolver-a-lista` | área INVENTARIO | 204 |

Endpoints de administración de reglas (`/api/v1/admin/lista-compra/...`): sin cambios salvo
`bloqueada` en la respuesta de `GET /eventos/{eventoId}`.

### DTOs

- `LineaCompraDto`: `+ long id`, `+ boolean comprada`. `cantidadCalculada` se mantiene (a 0,
  para el bloque 2).
- `ListaCompraResponse`: `+ boolean bloqueada`.
- `ListaCompraAdminResponse`: `+ boolean bloqueada`.
- `ArticuloDto` (inventario): `+ BigDecimal cantidadComprada`.
- `CambiarBloqueoRequest`: `record(boolean bloqueada)`.

### Excepciones nuevas (`ApiExceptionHandler`)

- `LineaCompraNoEncontradaException` → `LINEA_COMPRA_NO_ENCONTRADA`, 404.
- `NadaQueDevolverException` → `NADA_QUE_DEVOLVER`, 400.

## Web (`front`)

### `lista-compra` (lectura)

- Cabecera: si `puedoEditar`, botón **"Bloquear lista"** / **"Desbloquear lista"** según
  `bloqueada`. Cuando `bloqueada`, texto "· lista bloqueada" junto al recuento.
- Tabla: columna extra de acción. Si `puedoEditar`, `!linea.comprada` y `linea.cantidad > 0`
  → botón **"Comprado"**. Si `linea.comprada` → fila atenuada + "✓ Comprada" (sin botón; se
  revierte desde el inventario de la fiesta).
- La alineación de columnas (`table-fixed` + `<colgroup>`) ya se corrige aparte; la columna
  de acción entra en ese `colgroup`.

### `inventario` (evento)

- Por artículo con `cantidadComprada > 0`: botón **"Devolver a la lista"**.
- El botón de devolver stock existente se muestra solo si la parte de stock es `> 0`
  (`cantidad − cantidadComprada > 0`) y se etiqueta "Devolver al inventario".

## Manejo de errores

- Línea inexistente o de otro evento → 404 `LINEA_COMPRA_NO_ENCONTRADA`.
- Devolver una fila sin parte comprada → 400 `NADA_QUE_DEVOLVER`.
- Evento oculto / inexistente → 404 `EVENTO_NO_ENCONTRADO` (como ahora).
- Sin permiso → 403 `SIN_PERMISO_INVENTARIO` (como ahora).
- Marcar comprada una línea ya comprada → 204 sin efecto (idempotente).
- Bloquear una lista ya bloqueada / desbloquear una ya desbloqueada → 204 sin efecto.

## Pruebas

### Backend

- `CalculadoraListaCompraTest`: sin cambios (el motor puro no se toca).
- `ListaCompraIT` (ampliar) / nuevo `ListaCompraSyncIT` (extiende `IntegrationTest`,
  eventos en el pasado con `oculto = false`, como el resto):
  - La lectura persiste líneas en `linea_compra_evento` y las reordena / actualiza cantidad
    al cambiar los apuntados.
  - Marcar una línea como comprada la congela: cambiar los apuntados no altera su cantidad
    ni la borra de la lista.
  - Bloquear detiene la sincronización: tras bloquear, apuntar a alguien nuevo no cambia
    ninguna cantidad.
  - Marcar comprada crea o suma en `articulo_evento` (`cantidad_comprada`), con
    `articulo_inventario_id` nulo cuando la fila es nueva.
  - `devolver-a-lista` resta solo `cantidad_comprada`, revierte la línea a pendiente y no
    toca la parte de stock; si no había stock, borra la fila.
  - `devolver-a-lista` sobre una fila sin parte comprada → 400 `NADA_QUE_DEVOLVER`.
  - Línea de otro evento → 404.

  - Enviar stock de un producto que ya se compró desde la lista fusiona en la misma fila.

## Fuera de alcance

- Arrastre de `linea_compra_evento` de un año al siguiente al cerrar el año.
- Edición por el administrador de líneas concretas con la lista bloqueada (las "excepciones"
  que el usuario anticipa; el modelo ya lo permite, la UI no).
- Descuento del inventario de la fiesta en el cálculo de la cantidad a comprar (bloque 2;
  `cantidadCalculada` ya viaja en el DTO para no necesitar migración entonces).
